# 需求分析：一键归档定时任务会话

- 插件：`dsh-archive-pro`
- 当前版本：1.0.0
- 目标版本：1.1.0
- 日期：2026-11-18

---

## 1. 需求描述

现有插件只管理**已归档**的会话：搜索、筛选、排序、多选、批量取消归档、永久删除。

新增功能：**一键归档定时任务触发的会话** —— 这批会话尚未归档，清理它们属于另一个场景。

核心动作：一个按钮，自动勾选全部由定时任务触发的会话，供主人确认后批量归档。

---

## 2. 已核实的现状（源码级）

### 2.1 归档动作

`ctx.workspaceRegistry.archiveSession(sessionId, { stopActivity: true })` 是 DSH 原生归档能力，现有插件的 `deleteSessionFromMenu()` 已在用它。

归档后会话进入 `workspaceRegistry.archivedSessionIds`，从侧边栏隐藏，但**文件和日志都还在**（永久删除是另一个动作）。所以「归档」是可逆的，符合主人「清理尚未归档的会话」的诉求。

### 2.2 定时任务如何创建会话

`@deepseek-ai/dsh-schedule` 的 `resolveTarget()`（`src/runtime.ts:425`）有三种 target：

| `target.kind` | 行为 | 是否新建会话 |
| --- | --- | --- |
| `session` | 每次投递到**用户已有的**会话 | ❌ 复用 |
| `new_once` | 首次投递创建一个会话，之后复用 | ✅ 首个是新建 |
| `new` | **每次投递都创建全新会话** | ✅ 每次新建 |

只有 `new` / `new_once` 产生的会话才是「定时任务触发的会话」。`session` 类任务用的是主人自己的会话，**绝不能**被这个功能误伤。

### 2.3 识别标记的难点

定时任务创建会话时调用：

```ts
await controller.create({ sessionId, cwd, agentPreset })   // src/runtime.ts:473
```

**没有任何 meta 标记**，会话 id 也是普通的 `session-${randomUUID()}`。所以无法从会话本身判断来源。

可靠来源是**定时任务自己的投递回执**：

```
ScheduleDeliveryReceipt {
  scheduledAt, deliveredAt, messageId,
  targetSessionId   // ← 这次投递落到哪个会话
}
```

`ScheduleService.history({ id, limit, before? })` 返回这个回执列表（分页，每页最多 100），`ScheduleService.list()` 返回所有任务。

因此识别算法：

```
for 每个任务 in schedule.list():
    if task.target.kind not in ('new', 'new_once'): 跳过
    翻页读取该任务的 history
    收集所有 records[].targetSessionId  → 定时任务会话集合
```

### 2.4 未归档会话列表

- 全部已存储会话：`ctx.sessionPersistence.list()` → `SessionPersistenceSnapshot[]`，含 `header`（`id`、`createdAt`、`cwd`）
- 已归档集合：`ctx.workspaceRegistry.archivedSessionIds`
- 两者相减 = 未归档会话

### 2.5 服务可用性

`schedule` 服务来自可选 bundle `@deepseek-ai/dsh-schedule`。**未安装时 `ctx.schedule` 为 undefined**，功能必须优雅降级（按钮置灰 + 说明），不能报错。

## 3. 功能设计

### F0 时间阈值（主人的补充要求）

**不能把正在跑的定时任务归档掉。** 因此归档对象必须满足「已经结束一段时间」。

判据采用**该会话最后一次投递距今的时间**：

| 任务状态 | 最后投递时间 | 是否可归档 |
| --- | --- | --- |
| active，刚投递 5 分钟 | 5 分钟前 | ❌ 太新 |
| active，2 小时前投递 | 2 小时前 | ✅ |
| ended | 通常很久前 | ✅ |

理由：

- 一次投递创建会话后，agent 随即执行该次任务；投递时间就是这次「运行」的开始时间
- 超过阈值即意味着这次运行早已结束
- 任务本身仍在 active 也无妨——下次触发会**新建**会话，归档历史会话不影响它继续跑
- 任务若已 `ended`，其最后投递通常远早于阈值，自然满足

**阈值可下拉调整**，默认值 **1 小时**：

| 选项 | 值 |
| --- | --- |
| 1 小时（默认） | 60 分钟 |
| 6 小时 | 360 分钟 |
| 24 小时 | 1440 分钟 |
| 7 天 | 10080 分钟 |
| 30 天 | 43200 分钟 |

阈值由客户端传入查询参数，**后端按阈值过滤**，保证页面上的统计数字与实际归档范围一致。

额外保护：任务的 `executionActive` 为真时（最新投递正在其复用目标会话中排队或运行）整份任务跳过。

### F1 新分区「定时任务会话」

现有页面拆成两个视图：

| 视图 | 内容 |
| --- | --- |
| **已归档会话** | 现有全部功能，不改动 |
| **定时任务会话** | 新增 |

### F2 一键勾选

「一键勾选定时任务会话」按钮：

1. 后端扫描定时任务投递历史，得出定时任务会话集合
2. 与未归档会话集合求交集
3. 前端自动勾选全部交集项
4. 显示统计：共发现 N 个定时任务会话，其中 M 个未归档，已勾选 M 个

### F3 批量归档

「归档所选」按钮：

- 对勾选的会话逐个调 `archiveSession(sessionId, { stopActivity: true })`
- **单个失败不中断整批**，最后汇总成功/失败数
- 归档成功后从列表移除（因为它变成已归档了）
- 归档失败保留在列表并显示原因

### F4 展示字段

定时任务会话列表显示：

- 标题（会话标题）
- 来源任务名（哪个定时任务产生的）
- 创建时间
- 工作区
- 大小
- 勾选框

### F5 安全约束

- **已归档的定时任务会话不显示**（主人要清理的是「尚未归档」的）
- **pinned（置顶）会话不自动勾选**，需要手工勾选
- 归档**不删除任何文件**，随时可在「已归档会话」分区取消归档或永久删除
- 后端对每个 sessionId 做格式校验（复用现有 `SESSION_ID_RE`）

### F6 边界与降级

| 情况 | 处理 |
| --- | --- |
| `schedule` 服务不存在 | 按钮置灰，提示未安装定时任务 bundle |
| 定时任务有但从未投递 | 无会话可归档，显示「0 个」 |
| 投递历史被保留策略裁剪 | 提示可能不完整（`earlierRecordsPruned`） |
| 会话已被主人手动删除 | 跳过，不报错 |

## 4. 实现方案

### 4.1 host 端（`lib/routes.js` + `lib/index.js`）

新增两条路由：

| 路由 | 方法 | 作用 |
| --- | --- | --- |
| `/dsh-archive-pro/scheduled-sessions` | GET | 扫描定时任务会话，返回可归档清单 |
| `/dsh-archive-pro/archive` | POST | 批量归档传入的 sessionId |

新增注入：`schedule`（可选）。因为可选服务不能用 `inject` 数组硬声明（会阻止插件加载），改用 `ctx.get('schedule')` 惰性读取。

新增导出函数：

- `listScheduledSessions(host)` —— 扫描并返回清单
- `archiveSessions(host, sessionIds)` —— 批量归档

### 4.2 客户端（`client/client.js`）

- 顶部加视图切换（已归档 / 定时任务会话）
- 新分区：按钮 + 列表 + 批量归档 + 统计
- 复用现有的选择状态、排序、批量操作模式

### 4.3 国际化

`locale/zh.json` + `locale/en.json` 补齐新文案。

## 5. 验收标准

1. 顶部可切换到「定时任务会话」分区
2. 点「一键勾选」后，所有未归档的定时任务会话被自动勾选
3. 统计数字正确（发现数 / 未归档数 / 勾选数）
4. 点「归档所选」后，这批会话从侧边栏消失，出现在「已归档会话」分区
5. 定时任务复用用户会话（`target.kind === 'session'`）的情况**不会被**勾选
6. 归档失败时给出原因，其余继续
7. 未安装定时任务 bundle 时按钮置灰并说明原因
8. 现有功能全部不受影响
9. **闲置时长阈值生效**：刚投递不足阈值的会话不纳入归档范围
10. **阈值可下拉调整**：1 小时 / 6 小时 / 24 小时 / 7 天 / 30 天，切换后列表与统计同步刷新
11. **正在执行的任务被跳过**：统计里显示跳过的任务数
12. 默认阈值为 1 小时

## 6. 风险

| 级别 | 风险 | 说明 |
| --- | --- | --- |
| 中 | 投递历史被保留策略裁剪 | 早期投递的会话可能识别不到，界面需提示 |
| 中 | 定时任务仍在运行 | 归档只影响历史会话，下次投递会新建；若要彻底断流应先暂停任务 |
| 中 | `new_once` 任务转为 `session` 后无法区分 | 该任务的会话可能漏检（保守取舍，优先保证不误伤主人自己的会话） |
| 低 | `schedule` 服务缺失 | 降级处理，功能不可用 |
| 低 | 归档过程中会话正活跃 | 用 `stopActivity: true` 停止活动，且闲置阈值已过滤掉新会话 |
